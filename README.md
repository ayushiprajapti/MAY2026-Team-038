# INTACH Pune Heritage Platform

A full-stack web platform built for the **INTACH Pune Conservation Chapter** — the local chapter of the Indian National Trust for Art and Cultural Heritage. It brings together heritage-site documentation, volunteer-driven site submissions, public event management, an AI heritage guide, and a heritage-goods shop into one system, serving both the public and INTACH's internal team through a role-based admin dashboard.

## What this platform does

INTACH Pune maintains records of hundreds of heritage sites across the city — forts, temples, wadas, stepwells, and other built and natural heritage — along with running walks, workshops, and community events, and selling heritage-themed merchandise to fund conservation work. This platform digitizes that work:

- **Heritage site database** — hundreds of documented sites (built, natural, craft, intangible heritage) with location, description, historical significance, and photos, browsable on an interactive map.
- **Volunteer submissions** — the public can submit newly-discovered or undocumented heritage sites with photos; INTACH staff review, approve, or reject each submission through an admin queue.
- **Dynamic heritage trails** — walkable trails auto-generated by clustering nearby approved heritage sites, rather than hand-curated.
- **Events** — heritage walks, workshops, quizzes, competitions, and cultural events, with public registration, waitlisting, and an admin dashboard for coordinators.
- **AI heritage guide** — a retrieval-augmented chatbot that answers visitor questions grounded in the actual heritage-site database.
- **Heritage shop** — an online store for INTACH's heritage-themed merchandise (books, crafts, maps, souvenirs), with cart, checkout, and admin inventory management.
- **Role-based access** — registered members, volunteers, event coordinators, heritage experts, shop admins, and system admins each see the appropriate slice of the platform.

## Architecture

```
┌─────────────────┐        ┌──────────────────┐        ┌─────────────────┐
│   React SPA      │  HTTP  │   FastAPI backend │        │   PostgreSQL     │
│   (frontend/)     │ ─────► │   (backend/)      │ ─────► │   + PostGIS      │
└─────────────────┘        └────────┬─────────┘        └─────────────────┘
                                      │
                       ┌──────────────┼──────────────┐
                       ▼              ▼              ▼
                   Redis          Cloudinary      NVIDIA LLM API
              (query caching)   (image storage)  (RAG chat + content
                                                   generation)
```

- **Frontend**: React SPA that talks to the backend over a REST API — no server-side rendering, no direct database access.
- **Backend**: FastAPI, talking to Postgres directly via `psycopg2` (no ORM) — see `backend/README.md`.
- **Database**: PostgreSQL with PostGIS for geographic queries (heritage site locations, trail clustering by distance).
- **Caching**: Redis, shared across backend processes, caching read-heavy queries (product listings, event listings, dynamic trails) with explicit invalidation on writes.
- **Images**: Cloudinary, organized by entity type (shop products, monuments, events, heritage submissions).
- **AI**: NVIDIA-hosted LLM, used for the RAG-based heritage chatbot and for content generation (e.g. backfilling missing site descriptions).

## Getting started

Setup and run instructions live in each subproject's own README, since the backend and frontend have independent environments and dependencies:

- **[backend/README.md](backend/README.md)** — Python environment, database setup, environment variables, running the API.
- **[frontend/README.md](frontend/README.md)** — Node environment, environment variables, running the dev server.

You'll generally want both running at once: the backend on `http://localhost:8000`, the frontend on `http://localhost:5173`.

## Database schema

`schema.dbml` is the canonical schema reference (viewable at [dbdiagram.io](https://dbdiagram.io)). The actual database is created from `backend/db/create_schema.py`, which should stay in sync with `schema.dbml` — see `backend/README.md` for how to apply it.
